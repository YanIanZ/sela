## Context

Sela v3 is a wellbeing app for real people aged 15 to 50 and over. Users keep personal notes ("Catatan pribadiku") across sessions, see a timeline, correct memory, prepare a consultation summary ("Ringkasan untuk konsultasi"), share chosen content and later export or delete it. That needs durable storage, identity that survives a browser restart, and a recovery path that does not depend on an email provider Sela does not have.

What exists today (read in this branch, commit `e9711af`):

- `internal/journey` + `internal/store`: a per-session-locked **memory** store (`journey.Store`), 256-bit session ids in an HttpOnly SameSite=Strict cookie, share tokens indexed by SHA-256, recipient principals bound to one handoff, idle/absolute expiry and a sweeper. A restart erases everything (SPEC C7, V23).
- `internal/httpapi`: strict JSON decoding (no unknown, case-variant or duplicate keys, depth 32, no trailing data), body limits, the mutation guard (`X-Sela-Request: 1`, `Origin`, `Sec-Fetch-Site`), a bounded LRU token-bucket limiter keyed by client address (IPv6 /64), localized `{"error":{code,message,field}}` envelopes (ID/EN), security headers, and metadata-only slog JSON request logs (route template, status, duration, request id).
- `internal/config`: environment-only configuration with bounded parsing, `SELA_ENV` in `production|development|test`, secrets never in `String()`.
- v1 (`services/persistence`, `supabase/migrations`): idempotent SQL re-run on every start with **no tracking table** ("skeleton runner"), `REVOKE ALL … FROM PUBLIC`, scrypt admin hashes, a stateless HMAC admin token, and Supabase twins with RLS. Reused here: `REVOKE … FROM PUBLIC`, `CHECK` constraints on enums and lengths, FK `ON DELETE CASCADE`, partial indexes. Not reused: the untracked runner (no checksum, lock or down path), stateless tokens (cannot be revoked or listed), and the browser-facing Data API model (Sela's browser never talks to the database).

Threats this design addresses: a stolen database dump or backup; one user reaching another's records; session theft or fixation; CSRF and login CSRF; credential stuffing and username enumeration; operator or log exposure of content; deletion that leaves readable copies in backups; demo or staging data mixing with real data; an unsafe data migration.

## Options considered

| Option | Durability and integrity | Concurrency and operations | Encryption and deletion | Fit | Verdict |
| --- | --- | --- | --- | --- | --- |
| **PostgreSQL 16 via `github.com/jackc/pgx/v5` v5.10.0** | WAL, transactional DDL (a failed migration rolls back), FKs with `ON DELETE CASCADE`, `CHECK` constraints, partial unique indexes | Many writers; advisory locks for the migrator and background jobs; schemas give each parallel test its own namespace; `pg_dump -Fc`/`pg_restore` for backup and restore drills; managed offerings exist in most regions | Column-level envelope encryption in Go; `bytea` for ciphertext; table-level dump selection lets wrapped keys be backed up separately from content (needed for crypto-shredding) | Local PostgreSQL 16.15 available here (observed); v1 already used PostgreSQL; a future second app instance can share it | **Chosen (PM decision D-027)** |
| SQLite (file, pure-Go driver) | Durable, transactional | One writer at a time; a second app instance cannot share the file; backups are file copies taken under a lock; parallel tests need one file each (fine) but production restore drills and point-in-time recovery are weaker | Same Go-level encryption possible; separating key backups from content backups requires two database files | Simple for one instance, but a new dependency, and a later move to a server database would be a second migration of real user data | Rejected: single-writer and single-host limits, plus a forced future data migration |
| Keep memory-only (v2 `internal/store`) | None: restart erases all data | Single instance only | Deletion is trivially complete | Contradicts the brief ("persistent, user-controlled personal notes", export, timeline across sessions) | Rejected for real use; **kept for development, demo and test only** (see Environments) |

pgx was chosen over `database/sql` + `lib/pq` because `lib/pq` is in maintenance mode and pgx gives native `uuid`, `bytea`, `timestamptz`, `jsonb` mapping, a pool (`pgxpool`) and `pgx.Tx` without reflection. No ORM and no migration library: the runner below is small, and its rules (checksums, data-migration gates) are Sela-specific.

### 3. Schema v1 (foundation, migration 0001)

Conventions for every migration in every range: ids are `uuid` generated in Go; times are `timestamptz` written from the Go clock (tests inject it); enums are `text` with `CHECK`; every table that holds a user's data has `user_id uuid NOT NULL REFERENCES users(id) ON DELETE CASCADE` (the single allow-listed exception is `user_data_keys`, below); `REVOKE ALL ON <table> FROM PUBLIC`; no extensions (so a per-test schema needs no superuser); encrypted columns are `bytea` named `*_ct`.

```sql
-- 0001_foundation.up.sql   (-- sela:kind schema)
CREATE TABLE instance_meta (
  singleton   boolean PRIMARY KEY DEFAULT true CHECK (singleton),
  environment text NOT NULL CHECK (environment IN ('development','test','demo','staging','production')),
  created_at  timestamptz NOT NULL
);

CREATE TABLE users (
  id                    uuid PRIMARY KEY,
  kind                  text NOT NULL CHECK (kind IN ('guest','account')),
  age_band              text NOT NULL CHECK (age_band IN ('15_17','18_plus','unknown')),
  age_band_source       text NOT NULL CHECK (age_band_source IN ('self_declared')),
  age_band_confirmed_at timestamptz NOT NULL,
  locale                text NOT NULL CHECK (locale IN ('id','en')),
  version               integer NOT NULL DEFAULT 1 CHECK (version > 0),
  created_at            timestamptz NOT NULL,
  last_active_at        timestamptz NOT NULL,
  upgraded_at           timestamptz NULL,
  guest_expires_at      timestamptz NULL,
  CHECK ((kind = 'guest') = (guest_expires_at IS NOT NULL))
);
CREATE INDEX users_guest_inactive ON users (last_active_at) WHERE kind = 'guest';
CREATE INDEX users_guest_expiry   ON users (guest_expires_at) WHERE kind = 'guest';

CREATE TABLE credentials (
  user_id                     uuid PRIMARY KEY REFERENCES users(id) ON DELETE CASCADE,
  username                    text NOT NULL UNIQUE CHECK (username ~ '^[a-z0-9][a-z0-9._-]{2,31}$'),
  password_hash               bytea NOT NULL CHECK (octet_length(password_hash) = 32),
  password_salt               bytea NOT NULL CHECK (octet_length(password_salt) = 16),
  argon2_version              smallint NOT NULL CHECK (argon2_version = 19),
  argon2_memory_kib           integer NOT NULL CHECK (argon2_memory_kib >= 19456),
  argon2_iterations           integer NOT NULL CHECK (argon2_iterations >= 2),
  argon2_parallelism          smallint NOT NULL CHECK (argon2_parallelism BETWEEN 1 AND 16),
  password_changed_at         timestamptz NOT NULL,
  failed_count                integer NOT NULL DEFAULT 0 CHECK (failed_count >= 0),
  last_failed_at              timestamptz NULL,
  next_attempt_at             timestamptz NULL,     -- dropped by 0002 (the backoff moved to login_throttle, §9)
  password_login_disabled_at  timestamptz NULL,
  recovery_generated_at       timestamptz NOT NULL,
  recovery_acknowledged_at    timestamptz NULL,
  created_at                  timestamptz NOT NULL
);

CREATE TABLE recovery_codes (
  user_id    uuid NOT NULL REFERENCES users(id) ON DELETE CASCADE,
  code_hash  bytea NOT NULL CHECK (octet_length(code_hash) = 32),
  created_at timestamptz NOT NULL,
  used_at    timestamptz NULL,
  PRIMARY KEY (user_id, code_hash)
);

CREATE TABLE sessions (
  id                   uuid PRIMARY KEY,
  user_id              uuid NOT NULL REFERENCES users(id) ON DELETE CASCADE,
  token_hash           bytea NOT NULL UNIQUE CHECK (octet_length(token_hash) = 32),
  kind                 text NOT NULL CHECK (kind IN ('guest','account')),
  trusted_device       boolean NOT NULL,
  device_browser       text NOT NULL CHECK (device_browser IN ('chrome','edge','firefox','safari','samsung','opera','other')),
  device_os            text NOT NULL CHECK (device_os IN ('android','ios','windows','macos','linux','chromeos','other')),
  created_at           timestamptz NOT NULL,
  last_seen_at         timestamptz NOT NULL,
  idle_timeout_seconds integer NOT NULL CHECK (idle_timeout_seconds > 0),
  absolute_expires_at  timestamptz NOT NULL,
  authenticated_at     timestamptz NOT NULL,
  rotated_from         uuid NULL,
  revoked_at           timestamptz NULL,
  revoke_reason        text NULL CHECK (revoke_reason IN ('logout','logout_all','revoked_by_user','rotated','password_changed','recovery','upgraded')),  -- 0003 adds 'restored'
  CHECK ((revoked_at IS NULL) = (revoke_reason IS NULL))
);
CREATE INDEX sessions_user_live ON sessions (user_id) WHERE revoked_at IS NULL;
CREATE INDEX sessions_cleanup   ON sessions (absolute_expires_at);

-- No FK on purpose: the row outlives the user as a destruction tombstone (§5, §11).
CREATE TABLE user_data_keys (
  user_id      uuid PRIMARY KEY,
  wrapped_dek  bytea NULL,
  kek_id       text NULL,
  dek_version  smallint NOT NULL DEFAULT 1 CHECK (dek_version > 0),
  created_at   timestamptz NOT NULL,
  rewrapped_at timestamptz NULL,
  destroyed_at timestamptz NULL,
  CHECK ((destroyed_at IS NULL) = (wrapped_dek IS NOT NULL AND kek_id IS NOT NULL))
);
CREATE INDEX user_data_keys_by_kek ON user_data_keys (kek_id) WHERE destroyed_at IS NULL;

CREATE TABLE consents (           -- current decision per purpose
  user_id        uuid NOT NULL REFERENCES users(id) ON DELETE CASCADE,
  purpose        text NOT NULL CHECK (purpose ~ '^[a-z][a-z0-9_]{1,47}$'),
  granted        boolean NOT NULL,
  policy_version text NOT NULL CHECK (char_length(policy_version) BETWEEN 1 AND 64),
  decided_at     timestamptz NOT NULL,
  revision       integer NOT NULL CHECK (revision > 0),
  PRIMARY KEY (user_id, purpose)
);
CREATE TABLE consent_events (     -- history, append-only
  id             uuid PRIMARY KEY,
  user_id        uuid NOT NULL REFERENCES users(id) ON DELETE CASCADE,
  purpose        text NOT NULL,
  decision       text NOT NULL CHECK (decision IN ('granted','withdrawn')),
  policy_version text NOT NULL,
  source         text NOT NULL CHECK (source IN ('onboarding','settings','upgrade','system')),
  decided_at     timestamptz NOT NULL
);
CREATE INDEX consent_events_user ON consent_events (user_id, decided_at DESC, id DESC);

CREATE TABLE guardian_consents (  -- ages 15-17; consent is not access
  id               uuid PRIMARY KEY,
  user_id          uuid NOT NULL REFERENCES users(id) ON DELETE CASCADE,
  relationship     text NOT NULL CHECK (relationship IN ('parent','legal_guardian')),
  method           text NOT NULL CHECK (method IN ('guardian_present_attestation')),
  guardian_name_ct bytea NULL,
  policy_version   text NOT NULL,
  granted_at       timestamptz NOT NULL,
  withdrawn_at     timestamptz NULL,
  withdrawn_by     text NULL CHECK (withdrawn_by IN ('user','operator')),
  CHECK ((withdrawn_at IS NULL) = (withdrawn_by IS NULL))
);
CREATE UNIQUE INDEX guardian_consents_one_active ON guardian_consents (user_id) WHERE withdrawn_at IS NULL;

CREATE TABLE audit_events (       -- append-only, no content
  id         uuid PRIMARY KEY,
  user_id    uuid NOT NULL REFERENCES users(id) ON DELETE CASCADE,
  at         timestamptz NOT NULL,
  type       text NOT NULL CHECK (type ~ '^[a-z_]+\.[a-z_]+$'),
  actor      text NOT NULL CHECK (actor IN ('user','system','recipient')),
  session_id uuid NULL,             -- no FK: sessions are purged, events stay
  detail     jsonb NOT NULL DEFAULT '{}'::jsonb
             CHECK (jsonb_typeof(detail) = 'object' AND octet_length(detail::text) <= 1024)
);
CREATE INDEX audit_events_user ON audit_events (user_id, at DESC, id DESC);

-- Append-only for the application: UPDATE is rejected; DELETE happens only
-- through the users cascade and the retention job.
CREATE FUNCTION sela_reject_update() RETURNS trigger LANGUAGE plpgsql AS
$$ BEGIN RAISE EXCEPTION 'append-only table %', TG_TABLE_NAME; END $$;
CREATE TRIGGER audit_events_append_only   BEFORE UPDATE ON audit_events   FOR EACH ROW EXECUTE FUNCTION sela_reject_update();
CREATE TRIGGER consent_events_append_only BEFORE UPDATE ON consent_events FOR EACH ROW EXECUTE FUNCTION sela_reject_update();

REVOKE ALL ON instance_meta, users, credentials, recovery_codes, sessions, user_data_keys,
  consents, consent_events, guardian_consents, audit_events FROM PUBLIC;
```

The down file drops these objects in reverse order. **Migration 0002 (`0002_login_throttle`, schema, review round 1)** adds `login_throttle (key_hash bytea PRIMARY KEY /* keyed username key, the rate-limit key */, failures integer, last_failed_at timestamptz)` with an index on `last_failed_at`, and drops `credentials.next_attempt_at` (the backoff moved to the throttle, §9; `failed_count` stays for the 100-failure disable). The table has no `user_id` and no username in clear: `key_hash` is `HMAC-SHA256(K, "u:" ‖ normalised username)` under a secret `K = HKDF-SHA256(current KEK, info "sela.login-throttle.v1")` that lives only in the server's memory, so the rows cannot be reversed with a dictionary without the KEK (amended after review round 2: the round-1 text said "SHA-256 of the normalised username" and "holds no username", but an unkeyed SHA-256 of a username, and of whatever else was typed into the field, is reversed by a plain dictionary). Input that is not a valid username (a passphrase or an email address typed into the username field) is never written to the table; only valid usernames, existing or not, are, for about an hour (two at most, with the hourly retention run). Rotating the KEK changes `K`, which only resets the throttle. The rows are left out of the content dump (`--exclude-table-data`); WAL archives, replicas and provider snapshots still hold them for their own retention, which is why the key is keyed. **Migration 0003 (`0003_session_restored`, schema, review round 2)** adds `restored` to the `sessions.revoke_reason` CHECK: `sela restore reconcile` revokes every session of a restored database with that reason (§11); its down file deletes those (already revoked) rows and restores the earlier CHECK. Field notes:

- **Age band, how it is collected:** one self-declared single-choice question at guest start or registration ("15–17 tahun", "18 tahun atau lebih", "Tidak ingin menjawab"; plus "Di bawah 15 tahun"). No birth date is ever stored (data minimisation). "Under 15" creates nothing and shows age-appropriate help information (`403 age_not_supported`). Which bands may sign up is configuration (`SELA_ALLOWED_AGE_BANDS`; production default `18_plus` until legal review clears minors, D-031; development, test, demo and staging default `15_17,18_plus,unknown`). `unknown` receives the protective defaults of `15_17` (age-appropriate copy, confidentiality explanation) and is treated as not 18+ wherever a provider's terms require adults (decided per provider in P5). The band can be corrected in settings; `age_band_confirmed_at` lets the UI ask a `15_17` user once a year whether it still applies. Self-declaration is not verification; its legal sufficiency is pending.
- **Guardian consent (15–17):** a record that a parent or legal guardian agreed, under a versioned guardian information text, captured on the young person's device (`guardian_present_attestation`), with an optional guardian name (encrypted). **Consent is not access:** there is no guardian account, principal, cookie, notification, report or export to the guardian; nothing the user writes is shared with a guardian by default or by this record. Whether a `15_17` user must have an active record before personal notes are stored is configuration (`SELA_GUARDIAN_CONSENT_REQUIRED`, default `true`) enforced by the feature milestones; the profile reports `required` and `status`. No guardian contact details are collected (no provider to contact them, and minimisation).
- **Username** is stored normalised (below) in plaintext because it is the login lookup key. The UI tells users not to use their real name; usernames that look like an email address, phone number or ID number are refused (reusing the v2 contact-detail detector).
- **Device label** is two closed enums derived from the User-Agent at session creation; the raw User-Agent and the IP address are never stored.

### 4. Migration runner (engineering default within D-027)

- **Embedded SQL:** `internal/db/migrations/NNNN_name.up.sql`, optional `NNNN_name.down.sql`, optional `NNNN_name.validate.sql`, all in one `embed.FS` so ordering is global. Names match `^[0-9]{4}_[a-z0-9_]{1,48}\.(up|down|validate)\.sql$`. Header directives in the up file's leading comments: `-- sela:kind schema|data` (required), `-- sela:requires NNNN[,NNNN]` (optional), `-- sela:irreversible` (no down file allowed), `-- sela:no-transaction` (refused for data migrations; not used in 0001).
- **The files cannot defeat the gates (review rounds 1 and 2):** the parser splits each file into statements the way the PostgreSQL server does (comments, quoted strings, dollar-quoted bodies and SQL-standard routine bodies understood; a body opens only with the token pair `BEGIN ATOMIC` in a `CREATE [OR REPLACE] FUNCTION|PROCEDURE` statement and closes only with an `END` that starts one of its inner statements, so a function named `begin` or a column labelled `end` or `case` cannot hide later statements, as they could from psql's own heuristic; a file that ends inside a body or a parenthesis is refused) and refuses, in the up, down and validate files of every migration that runs in the runner's transaction, any transaction-control statement (`BEGIN`, `START TRANSACTION`, `COMMIT`, `END`, `ROLLBACK`, `ABORT`, `SAVEPOINT`, `RELEASE`, `PREPARE TRANSACTION`, `COMMIT/ROLLBACK PREPARED`): one would end the runner's transaction early, so a failed validation could not roll back, a dry run would persist the change and nothing would be recorded. A validate file must be exactly one query; an empty or comment-only one is refused. Transaction control inside a routine body is refused too. As a second guard, after every up, validate and down file the runner checks that the connection is still inside **its own** transaction, comparing `pg_current_xact_id()` before and after the file (a file ending in `COMMIT; BEGIN;` is in a transaction again, but in a new one), and otherwise stops with `ErrTransactionEnded` (it never reports a rollback that did not happen).
- **Reserved ranges** (a test rejects a version outside them): 0001–0099 foundation, 0100–0199 conversation, 0200–0299 journal and check-in, 0300–0399 memory, 0400–0499 consultation summary and sharing, 0500–0599 AI routing records, 0600–0699 reading content, 0700–0799 planned-care directory and synthetic sandbox, 0900–0999 ops. Each range is owned by its milestone. Pending migrations run in numeric order; a pending version lower than the highest applied one is allowed (reported `out_of_order`) only when every version it `requires` is applied, because ranges own disjoint tables. "Last" for `down-last` means the most recently applied (`applied_seq`), not the highest number.
- **`schema_migrations`**, created by the runner itself (not by 0001):

  ```sql
  CREATE TABLE IF NOT EXISTS schema_migrations (
    version        integer PRIMARY KEY CHECK (version BETWEEN 1 AND 9999),
    name           text NOT NULL,
    kind           text NOT NULL CHECK (kind IN ('schema','data')),
    checksum       bytea NOT NULL,      -- SHA-256 of the up file, CRLF normalised to LF
    down_checksum  bytea NULL,          -- SHA-256 of the down file at apply time; down-last refuses another one
    applied_seq    bigint GENERATED ALWAYS AS IDENTITY UNIQUE,
    applied_at     timestamptz NOT NULL DEFAULT now(),
    applied_by     text NOT NULL DEFAULT current_user,
    duration_ms    integer NOT NULL,
    backup_ref     text NULL,
    binary_version text NOT NULL
  );
  ```

  A mismatching checksum of an applied migration, or an applied version the binary does not embed ("schema ahead of binary"), stops `up` and stops server start. `.gitattributes` gains `*.sql text eol=lf` so checkouts do not alter bytes; the CRLF normalisation is a second guard.
- **Advisory lock:** every command takes `pg_advisory_lock(hashtextextended('sela.migrate:' || current_schema(), 0))` on a dedicated connection and releases it at the end. Keying by schema serialises concurrent runners on one database while letting parallel tests (one schema each) proceed. The background jobs (purge, retention) use their own key the same way, so only one instance runs them.
- **Commands** (`sela migrate <cmd>`, reading `SELA_DATABASE_URL`):
  - `status` — every embedded and applied version with state `applied | pending | out_of_order | checksum_mismatch | unknown_in_database`, kind, applied time, and the environment marker; exit 0 when current, 3 when pending, 4 on mismatch/unknown or when the marker names another environment than `SELA_ENV`.
  - `up [--to NNNN] [--backup-ref REF]` — applies pending migrations, each in its own transaction together with its `schema_migrations` row (PostgreSQL DDL is transactional, so a failure leaves nothing half-applied).
  - `dry-run` — applies every pending migration inside one transaction, runs validate files, prints per-migration duration and validation counts, then **rolls back**; nothing changes, not even `schema_migrations`. `no-transaction` migrations are reported as not dry-runnable and fail the dry-run.
  - `down-last --confirm NNNN` — runs the down file of the most recently applied migration (the confirm value must equal it) in one transaction and deletes its row; refuses another environment's database (like `up` and `dry-run`), `irreversible` migrations (rollback is then a restore), a data migration without `--backup-ref`, and a down file whose checksum differs from the `down_checksum` recorded when the migration was applied (exit 4; `status` names the drift on the applied row without blocking `up` or server start; a row recorded without a down checksum has nothing to compare and is accepted). Amended after data review round 3: the column was written but never compared, so a binary whose down file had drifted ran it silently, deleted the row and reported success while the schema stayed.
- **Server start:** never applies data migrations. In `production`, `staging` and `demo` it refuses to start while anything is pending or mismatched (message names the command to run). In `development` and `test`, `SELA_DB_AUTO_MIGRATE=true` may apply pending **schema** migrations at start.
- **Data migrations** (`kind data`, any migration that rewrites or moves existing user rows) additionally require, and the runner enforces what it can:
  1. **Backup:** a fresh `pg_dump -Fc` verified with `pg_restore --list`; its reference is passed as `--backup-ref` and stored in `schema_migrations.backup_ref` (refused without it).
  2. **Dry-run:** `sela migrate dry-run` against a restored copy of the target database in an isolated scratch database, never against a copy placed in staging or demo; result recorded in the PR.
  3. **Ownership validation:** a `validate.sql` file is mandatory; it runs inside the migration transaction and must return zero rows (for example rows whose `user_id` changed, rows whose owner no longer exists, ciphertext moved to another record, counts per owner that differ from before). Any row aborts and rolls back.
  4. **Rollback:** a reviewed down file, or `irreversible` plus the documented restore from the step-1 backup.
- **Tests:** `dbtest.New(t)` reads `SELA_TEST_DATABASE_URL`; when it is unset the test calls `t.Skip`, unless `SELA_REQUIRE_DB_TESTS=1` (set in CI), in which case it fails. It creates schema `t_<16 hex>`, opens a pool whose connections `SET search_path` to it, runs `up`, and registers `DROP SCHEMA … CASCADE` in `t.Cleanup`, so DB tests call `t.Parallel()`. Locally: `postgres://sela:sela-dev-only@127.0.0.1:5432/sela_test?sslmode=disable` (role `sela` can create schemas; observed). CI: the Go job of `.github/workflows/v2.yml` gets a `postgres:16` service with a health check and sets `SELA_TEST_DATABASE_URL` and `SELA_REQUIRE_DB_TESTS=1`.

### 5. Envelope encryption (PM decision D-028; parameters engineering default)

- **KEK** (key-encryption key): 32 bytes from the secret manager, injected as `SELA_DATA_KEK` (standard base64, must decode to exactly 32 bytes) with `SELA_DATA_KEK_ID` (`^(dev|test|demo|staging|prod)-[a-z0-9-]{1,40}$`; the prefix must match `SELA_ENV`, so a demo key cannot be loaded by production and vice versa). Keys being retired are listed in `SELA_DATA_KEK_PREVIOUS` (`id:base64,…`) and used only to unwrap. `sela keys generate-kek` prints a fresh key for the operator to store in the secret manager; the server never generates or persists a KEK. Config `String()` and logs show the KEK id only.
- **DEK** (data-encryption key): 32 random bytes per user, created in the same transaction as the user, stored only wrapped: `wrapped_dek = AES-256-GCM(KEK, nonce, DEK, AAD = "sela.dek.v1" ‖ user_id ‖ kek_id ‖ dek_version)`. The DEK itself never changes for the life of the user (KEK rotation re-wraps it), which is what makes crypto-shredding work with older backups.
- **Field encryption:** AES-256-GCM with the user's DEK, a fresh 96-bit random nonce per seal. Stored format: `0x01 ‖ nonce(12) ‖ ciphertext ‖ tag(16)` in a `bytea` column. **AAD binds every ciphertext to its place:** `"sela.aad.v1"` followed by length-prefixed (uvarint) `user_id`, `record_kind` (e.g. `guardian_consent`, `journal_entry`), `record_id` and `field` (e.g. `guardian_name`). A ciphertext copied to another user, record, kind or field fails authentication instead of decrypting. Random nonces stay far below the 2^32-messages-per-key bound of NIST SP 800-38D for any per-user volume the feature caps allow.
- **API:** `vault.Seal(ctx, userID, vault.Ref{Kind, RecordID, Field}, plaintext)` / `vault.Open(...)`; `vault.CreateUserKey(ctx, tx, userID)`; `vault.Destroy(ctx, tx, userID)`; `vault.Rewrap(ctx, batchSize)`. Unwrapped DEKs are cached in process for at most 5 minutes in a bounded LRU (default 1024 users), evicted at once on destroy, and never logged or serialised.
- **KEK rotation:** put the new key in `SELA_DATA_KEK`/`_ID`, move the old one to `SELA_DATA_KEK_PREVIOUS`, restart, run `sela keys rewrap` (batches of 500 rows: unwrap with the old KEK, wrap with the new, `UPDATE … WHERE kek_id = old`, idempotent and resumable), confirm `sela keys status` reports zero DEKs under the old id, then remove it from the environment. Keep the old KEK in the secret manager until the key-backup retention (§11) has passed, then destroy it. A suspected **DEK** exposure (key table and KEK both leaked) needs re-encryption of that user's data under a new DEK; that tool is not part of v1 (consequence below).
- **Crypto-shredding:** account deletion sets `wrapped_dek = NULL, kek_id = NULL, destroyed_at = now()` in the same transaction that deletes the user (§10). Because wrapped keys are backed up separately and briefly (§11), every copy of that user's content in older content backups becomes unreadable once the key backups that still hold the wrapped DEK expire; a restored backup is also reconciled (§11).
- **What is encrypted:** everything a user writes or selects about themselves and everything derived from it: conversation messages, journal text, check-in answers including scale values and chosen tags, memory items and corrections, AI summaries and interpretations, consultation summaries, share projections, upload contents and names, titles, free-text reasons, and in the foundation the guardian name. **What stays plaintext, minimal:** ids, `user_id`, timestamps, record kind and status enums, version and revision numbers, expiry times, consent purposes/versions/decisions, age band, locale, username, device enums, audit event types with allow-listed non-content details. Each feature migration lists its plaintext columns with the reason (authorization, ordering, expiry, retention or a state machine) and review rejects any other. Consequence: no server-side full-text search or analytics over content; search runs per user in the app after decryption.
- **Transit and rest:** HTTPS to the browser (HSTS `max-age=31536000` added in production); database connections outside loopback/unix sockets require `sslmode=verify-full` in staging and production (config refuses otherwise; it checks the settings pgx will connect with, for the primary host and every fallback, so a host or `sslmode` taken from `PGHOST`, `PGSSLMODE` or a libpq service file cannot bypass the rule); disk encryption by the host; backup files encrypted at rest by the backup storage (tool chosen in P7).

### 6. Authentication and recovery (PM decision D-029; parameters engineering default)

- **Username:** trimmed; must be ASCII (non-ASCII is refused with an explanation rather than folded, which avoids homoglyph look-alikes); lower-cased; 3–32 characters of `a-z 0-9 . _ -`, starting with a letter or digit; reserved names refused (`admin`, `sela`, `support`, `root`, `system`, `guest`, `moderator`, `official`, `help`, `security`, …); email-, phone- and ID-number-like strings refused. Case-insensitive uniqueness follows from storing the normalised form.
- **Password:** NFKC-normalised, then **15 to 256 Unicode code points** (and at most 1024 bytes); any character allowed, including spaces and emoji; no composition rules; no periodic expiry; refused if it equals or contains the username, or appears in the embedded blocklist (common and breached passwords from a permissively licensed list whose source and licence are recorded with the file, plus context words such as `sela`, `dengarin`, `selaapp`). The 15-character minimum follows NIST SP 800-63B-4 for single-factor passwords (observed); the UI encourages a passphrase of several words and shows the rule up front. **Paste, autofill and password managers are allowed** (`autocomplete="username"`, `"current-password"`, `"new-password"`; no paste blocking); there is **no CAPTCHA, puzzle or other cognitive function test** at any step, which satisfies WCAG 2.2 SC 3.3.8 Accessible Authentication (Minimum) through its "mechanism" exception (observed: the Understanding document lists password managers and copy-paste as such mechanisms).
- **Hashing:** argon2id (`golang.org/x/crypto/argon2.IDKey`), 16-byte random salt, 32-byte tag, **m = 64 MiB (65536 KiB), t = 2, p = 1** by default, configurable with the floor m ≥ 19456 KiB and t ≥ 2 (the OWASP Password Storage Cheat Sheet's minimum "19 MiB, 2 iterations, parallelism 1"; observed). The parameters are stored per row; on a successful login with parameters that differ from the current configuration, lower or higher, the password is re-hashed in the same transaction (amended after review round 2: only lower ones were before, so lowered parameters never converged), and only while the stored hash is still the one the login verified (§9, a proof commits only while its password is current). Hashing runs behind a semaphore (`SELA_AUTH_HASH_CONCURRENCY`, default 2, so at most 128 MiB is in use) with a 5-second wait, after which the request gets `503 server_busy`. Comparisons use `crypto/subtle`. No pepper (another long-lived secret whose rotation would invalidate every hash; argon2id cost is the defence); recorded as revisable.
- **Uniform failures (amended after review round 2):** an unknown username runs one argon2id verification against a dummy hash and returns the same `401 invalid_credentials` body as a wrong password. The dummy's parameters follow the parameters the stored credentials use: the server reads `SELECT argon2_memory_kib, argon2_iterations, argon2_parallelism, count(*) FROM credentials GROUP BY 1, 2, 3` at start and every 10 minutes (outside any request, so a login's statements stay the same), keeps one dummy per tuple, and maps each unknown username to one tuple by its keyed username key in proportion to the counts, **by fraction**: the key's first 64 bits, read as a number in [0, 1), are scaled to the total (`hi64(k × total)`), and the tuples own consecutive ranges. A repeated username therefore repeats its cost, and when the counts change (a registration, a guest upgrade, a deletion, a re-hash on sign-in) only the unknown usernames between the old and the new boundary of two tuples change cost, as many as the boundary moved: one registration among N accounts moves about p/N of them, one re-hash about 1/N, the rate at which existing accounts change cost when they re-hash (amended after review round 3, R3-1: the round-2 mapping took `k mod total`, which re-drew every unknown username whenever the total changed, so at each 10-minute refresh after any registration about 2p(1−p) of them flipped between the cheap and the dear cost while existing accounts kept theirs; one failed login per username per refresh, within the per-username limit, separated unknown from existing usernames). A fixed dummy at the configured parameters (the round-1 design) made every not-yet-re-hashed account cheaper (after a raise) or dearer (after a lowering, permanently) than an unknown username, a perfect one-request oracle after any parameter change. Residual (accepted for a controlled pilot and revisited before a public release, [D-055](../DECISION_LOG.md#d-055)): between a change and the next refresh (at most 10 minutes) and for an attacker who knows a particular account's history (for example that it has not signed in since the change), the cost still carries that information; an unknown username near a boundary changes cost once when the boundary passes it, which an attacker watching that username over a long time can see, though an existing account changes cost the same way when its owner signs in; a **KEK rotation** changes the throttle secret and so every username key, which re-maps all unknown usernames at once: while more than one tuple is in use, a failed login measured before and after a rotation can show an unknown username changing cost where an existing account does not (rotate the KEK while one parameter tuple is in use where possible; RUNBOOK §9); input that is not a valid username skips the database entirely and is distinguishable only in that it cannot exist, which the public username rules already say. Registration necessarily reveals that a username is taken (`409 username_taken`); it is rate limited.
- **Recovery codes:** 10 codes generated at registration and at guest upgrade, each 16 characters of Crockford base32 (80 bits), shown as `XXXX-XXXX-XXXX-XXXX` **once**, with copy and download buttons and a "Saya sudah menyimpannya / I have saved them" acknowledgement (`recovery_acknowledged_at`; until it is set the app keeps offering regeneration). Stored as `SHA-256("sela.recovery.v1" ‖ user_id ‖ normalised code)`; 80 bits make offline guessing infeasible without a slow hash, and binding the user id prevents cross-account lookups. Entry ignores case, spaces and hyphens and maps `O→0`, `I/L→1`. **Single use:** `UPDATE recovery_codes SET used_at = now() WHERE user_id = $1 AND code_hash = $2 AND used_at IS NULL` in the same transaction as the password reset, after `SELECT … FROM credentials WHERE username = $1 FOR UPDATE`; for an unknown username the same update runs against a random user id, so every failure sends the same statements (begin, lock, update, rollback; review round 2).
- **Recovery:** username + one code + a new password. On success: new hash, `failed_count` and `password_login_disabled_at` cleared, **every session revoked** (`recovery`), a new session created, audit `recovery.used` with the remaining count. All failures (unknown user, wrong or used code) return the same `401 recovery_failed`. Regeneration (`POST /auth/recovery-codes`) requires the current password, locks the account's credentials row (`FOR UPDATE`, so overlapping regenerations and a recovery serialise; without it two overlapping regenerations left both batches valid under READ COMMITTED, review round 2), deletes every old code and returns 10 new ones once. Under the same lock it is refused (`403 current_password_incorrect`, recorded as a failed attempt, the codes unchanged) when a recovery or a password change replaced the password while it was being verified, and, once, when an overlapping sign-in re-hashed it (§9, residual; amended after the PR #9 review, F1).
- **No email:** there is no email provider (pending; blocker **B-11** "email provider for verification and recovery" in [blockers](../BLOCKERS.md); an earlier version of this ADR proposed it as B-8, which in the blockers list is the Anthropic key). No email address is collected. Email verification and email recovery wait for that blocker, a separate consent and an ADR.
- **Passkeys (WebAuthn): deferred**, not rejected. Reasons: a WebAuthn server library would be a new dependency (or a substantial in-house implementation of attestation and CBOR parsing); the pilot's shared and family devices make device-bound credentials a recovery risk without a second factor or email; and the accessible password path above already meets SC 3.3.8. Revisit in P7 as an additional method.

### 7. Guest mode (PM decision D-029)

- `POST /api/v3/auth/guest` creates a server-side `users` row with `kind = 'guest'`, a DEK and a guest session bound to the HttpOnly session cookie. There are no credentials: **the cookie is the only key**.
- **Where and how long, stated in the UI and the policy before the guest starts:** the data is stored on Sela's server in a PostgreSQL database (the hosting region, named by `SELA_DATA_REGION_LABEL` once decided under B-15 (with the host, B-3), is shown in the notice and the profile), with personal content encrypted per user; it is deleted automatically after **7 days without activity** (`SELA_GUEST_INACTIVE_TTL`, default `168h`, bounds 1h–30d) and at the latest **30 days after creation** (`SELA_GUEST_MAX_AGE`, default `720h`, bounds 1d–30d), the latter because a guest cannot re-authenticate, so 30 days is also the guest session's absolute lifetime (NIST AAL1 recommends an overall timeout of at most 30 days; observed). Both dates are in the profile (`inactivePurgeAt`, `maxAgePurgeAt`); the UI warns from 7 days before the maximum age. If the cookie is lost (private window closed, browser data cleared, another device), the data cannot be opened again and is deleted on schedule.
- **No absolute anonymity is promised.** Copy (ID/EN, owned by UX, reviewed by the PM) says: no name or email is needed; the server still sees the connection's IP address for security and rate limiting (not stored in the database); the hosting provider and Sela's operators run the infrastructure; the content is encrypted but Sela's server can decrypt it to show it to you and to run the features you choose. Forbidden phrasings include "anonim sepenuhnya", "tidak bisa dilacak", "completely anonymous", "untraceable".
- **Purge job:** every 10 minutes, under the job advisory lock, up to 100 guests with `last_active_at < now - inactive TTL` or `guest_expires_at < now` are deleted through the same path as account deletion (§10, crypto-shredding included). Counts only are logged. Like the retention job, it runs every statement and transaction on the connection that holds its lock (`db.WithJobLock`) and takes no other one from the pool, so a job needs one connection and every accepted pool size works (`SELA_DB_MAX_CONNS` 1–200; amended after the PR #9 review, F2: the jobs queried through the pool while that connection held the lock and waited forever at 1, blocking every request until shutdown).
- **Upgrade** (`POST /auth/guest/upgrade` with username and password from a guest session) keeps the **same `user_id`**, so every owned row stays; it inserts credentials and recovery codes, sets `kind = 'account'`, `upgraded_at`, clears `guest_expires_at`, rotates the session (`upgraded`) and writes `account.upgraded`, all in one transaction.
- Guest capacity: `SELA_MAX_GUEST_ACCOUNTS` (default 10000) live guests, beyond which guest start returns `503 server_busy`, plus the per-client rate limit (§9).

### 8. Sessions and CSRF (engineering default within D-029)

- **Token:** 32 bytes from `crypto/rand`, base64url without padding (43 characters) in the cookie; the database stores only `SHA-256(token)` and looks sessions up by that hash. Tokens never appear in URLs, logs, audit details or responses.
- **Cookie:** `__Host-sela_auth` (`Secure`, `Path=/`, no `Domain`, `HttpOnly`, `SameSite=Strict`). When `SELA_SECURE_COOKIES=false` (plain-HTTP development only) the name is `sela_auth` without `Secure`. Untrusted-device sessions get no `Max-Age` (removed when the browser closes); trusted-device and guest sessions get `Max-Age` up to the absolute expiry. The v2 cookie `sela_session` (Path `/api/v2`) is unaffected.
- **Timeouts** (configurable within bounds; idle measured from `last_seen_at`):

  | Session | Idle | Absolute |
  | --- | --- | --- |
  | Account, `rememberDevice: false` (default) | 2 h (`SELA_SESSION_IDLE`) | 12 h (`SELA_SESSION_ABSOLUTE`) |
  | Account, `rememberDevice: true` | 7 days (`SELA_SESSION_TRUSTED_IDLE`) | 30 days (`SELA_SESSION_TRUSTED_ABSOLUTE`, max 30 days) |
  | Guest | guest inactive TTL (7 days) | guest maximum age (30 days from guest creation) |

  `last_seen_at` and `users.last_active_at` are written at most once per minute per session. An expired or revoked session returns `401 not_signed_in` (a v3 code; the v2 `session_missing` message speaks of the demo) and clears the cookie; expired and revoked rows are deleted 30 days later by the retention job.
- **Rotation:** a new token and row (with `rotated_from`), and the old row revoked, on login (any cookie already present is revoked first, which also defeats session fixation), guest upgrade, password change and recovery. There is no grace period for the old token.
- **Reauthentication:** `authenticated_at` records the last password proof. For accounts, exporting data and deleting the account require a password proof within `SELA_REAUTH_WINDOW` (default 10 minutes; `POST /auth/reauth`), else `403 reauth_required`. Guests have no password; their cookie is the proof.
- **Management:** users list their live sessions (device enums, created, last seen rounded to the hour, expiries, `current`), revoke any of their own, and sign out everywhere (`POST /auth/logout-all`, optionally keeping the current session). Password change revokes all other sessions.
- **CSRF:** every `/api/v3` mutation goes through the existing `mutation` wrapper (`X-Sela-Request: 1`, same `Origin` or `SELA_PUBLIC_ORIGIN`, no cross-site `Sec-Fetch-Site`, JSON content type, body limit, rate limit), including login and registration (login CSRF). With `SameSite=Strict` this needs no CSRF token. No CORS.

### 9. Rate limiting and backoff (engineering default)

The existing in-memory limiter gains per-bucket rate, window and burst, and buckets keyed by the keyed username key (§3: `HMAC-SHA256(K, "u:" ‖ normalised username)`, or of `"r:" ‖` the trimmed lower-cased input when it is not a valid username) besides the client key (IPv4 address or IPv6 /64, `SELA_TRUST_PROXY` rules unchanged). Every refusal is `429 rate_limited` with `Retry-After` in whole seconds.

| Action | Per client key | Per username (exists or not) | Other |
| --- | --- | --- | --- |
| Login | 20/min, burst 10 | 10/hour, burst 5 | Per-account backoff below |
| Register, guest upgrade | 20/hour, burst 5 (school and campus NATs share one address) | — | — |
| Guest start | 30/hour, burst 10 | — | Live-guest cap |
| Recovery | 10/hour, burst 3 | 5/hour, burst 3 | — |
| Reauth, change password, regenerate codes | 10/hour per session | — | Wrong current password counts as a failed login |
| Export | 6/hour per user | — | — |
| Other `/api/v3` mutations / reads | existing `mutation` 180/min, `read` 600/min | — | — |

**Backoff (amended after review rounds 1 and 3):** after 5 consecutive failures for a username key, each further attempt must wait `min(2^(failures−5) s, 15 min)`. The count lives in one place for every username key, known or unknown: the `login_throttle` table (migration 0002, keyed by the keyed rate-limit key, §3). Input that is not a valid username cannot name an account and is not persisted (it gets the same argon2id work and the same `401`, limited by the in-memory buckets only). A throttled response and its `Retry-After` are therefore identical for an existing and an unknown username, also after a restart or with several instances (the earlier design kept unknown usernames in a per-process LRU and existing accounts in `credentials`, so a deploy made them answer differently). The count decays after an **observation window of 1 hour** without a failure (longer than the longest wait, so it never shortens one); the retention job deletes such rows. A success (password, recovery code, reauthentication, password change, code regeneration) and account deletion clear it.

**Every password proof is reserved before its argon2id work (review round 3, R3-3).** One statement (`reserveSQL`) locks the account's credentials row (none for an unknown username), upserts the username key's throttle row with one more failure unless a backoff applies, and, when it did, adds one to `credentials.failed_count`; otherwise it reads the throttle row's latest state under its lock for the `Retry-After`. The attempt counts as a failure from that moment: a failed proof only finishes it (`recordFailureSQL`: the disable at the ceiling and the coalesced audit events), a success undoes it in its own transaction (`failed_count = 0`, throttle row deleted), and a reservation whose proof never ran (the hashing slots stayed busy, or the request ended while waiting for one) is given back. The round-2 gate only read the counts and recorded the failure after the verification, so concurrent attempts all passed one read: once a wait expired, five guesses (the per-username burst) ran instead of one, about 10 per hour instead of the schedule's 4. **The 100-attempt ceiling** (the NIST SP 800-63B-4 limit of 100 consecutive failed attempts; observed; `failed_count` does not decay) counts reserved attempts, so at most 100 proofs are ever verified after the last success: a reservation is refused while 100 are counted and one is in flight (a short `rate_limited`; an attempt that never reports back counts as failed after one minute), the failure that completes the 100th disables password sign-in (`403 password_login_disabled`) until recovery with a code, and **every success transaction re-checks the disable under the credentials row lock** (`… WHERE password_login_disabled_at IS NULL`), so a right password that passed the reservation before the 100th failure was recorded is refused instead of signing in on a disabled account (the round-2 code issued it a session). Consequence: when the 100th counted attempt is the right password while an earlier counted one is still failing, it is refused too; the account is under an attack of 100 guesses by then. The disable discloses that the username exists, which registration already does. **Same work for both:** a failed proof runs, for known and unknown usernames alike, the reservation statement, one argon2id verification and the failure statement; a pgx tracer test checks that both paths send identical statements. Round-2 measurements through a 1 ms one-way network proxy (300 usernames per side): the database part of a failed login differed by about 0.3–0.4 ms (the server-side row update), against about 10 ms of extra round trips before; whole logins with the production argon2id parameters (80 per side) showed median differences of +1.4 ms and +5.1 ms in two runs with p10 and minimum differences of either sign, single-request classification at chance (84/160, 92/160). Since round 3 the known side takes the credentials row lock and the update in the reservation (one row update per failed login, as before, plus the lock); not re-measured. The per-username limits allow only a handful of samples, which is why the remaining difference is accepted for a controlled pilot (D-055). Residual, by design: a username that just had ≥5 failures shows a backoff for up to the observation window, whoever caused them. `auth.login_failed` audit events are coalesced to one per account per hour with a count, so an attack cannot flood the table.

**A proof commits only while its password is current (amended after the PR #9 review, F1).** The argon2id verification runs outside any lock, between the reservation and the success transaction. A sign-in's success transaction therefore first locks the credentials row and compares the stored hash (tag and salt) with the one it verified (`lockProof`); when a password change or a recovery replaced it meanwhile, the proof is for a password that is no longer current, and nothing is committed: no session, no re-hash, no counter reset. Before, the old password still signed in after the change (the change revoked every session first, so the new one survived that revocation), and on the re-hash path it overwrote the new hash with a hash of the old password, which then kept working and the new one did not. **The refused proof is recorded as a failed attempt:** the answer is the wrong-password one (`401 invalid_credentials`), its reservation is not undone and the failure statement runs (`recordFailureSQL`: the disable at the ceiling, the coalesced `auth.login_failed`), because from the account's point of view it is a guess with a password that is not its own, and the owner's audit trail shows that the old password was tried. (A change or recovery that commits after the reservation has already reset the counters, so the attempt is not counted again.) Code regeneration takes the same check under its credentials lock (`403 current_password_incorrect`, counted the same way): its transaction does not check that the session is live, so the holder of the old password received a fresh batch of codes after the owner's recovery and could recover the account again. Reauthentication and password change commit only while the current session is live, under the credentials row lock, and every password change and recovery revokes every session of the user in the transaction that replaces the hash (a change rotates its own session), so a stale proof there already ends in `401 not_signed_in` with nothing committed; tests pin this. Deletion verifies no password itself but checks the session's recent proof, and now locks the credentials row before that check, so a change or recovery in flight is waited for and the deletion then refused (before, one that committed between the check and the delete left a deletion by a session it had just revoked). Recovery checks and consumes its code under the credentials row lock in the transaction that replaces the password, so it cannot go stale; guest upgrade verifies no secret (the guest's cookie is checked by the session lookup, the kind is re-checked under the users row lock and the rotation requires the session to be live); export is a read in one repeatable-read snapshot taken with its proof check, equivalent to an export just before a concurrent change. The check runs only after a successful verification, so the failure path of known and unknown usernames is unchanged. Residual (accepted; availability and audit accuracy only): the check compares the stored hash, not the password, so a re-hash looks like a replacement. A proof of the right, current password that overlaps a sign-in which re-hashes the stored hash (after a parameter change, or while instances run with different parameters, as during a rolling deploy of one) is refused once, whether or not it would re-hash itself: a sign-in gets `401 invalid_credentials` and a code regeneration `403 current_password_incorrect`. Nothing is committed (no session, no codes; the other sign-in's hash stays) and the proof succeeds when sent again. Each refusal writes the coalesced `auth.login_failed`, so the owner's trail shows a failed attempt although the password was right; no counter is raised, because the re-hashing sign-in reset them after the refused proof's reservation. Reauthentication and password change check the session, not the hash, and are not affected. Telling a re-hash from a replacement would need a password version; `password_changed_at` is a time, which a fixed clock (or a change within the same microsecond) leaves equal, so it is not used.

**Lock order (review round 3, R3-2):** every statement and transaction that touches more than one of them locks the account's `credentials` row first, then the username key's `login_throttle` row, then the user's `sessions` rows: the reservation, a successful login, reauthentication, password change (which before locked its session row first and deadlocked against a recovery, which revokes every session of the user after locking the credentials row), code regeneration, recovery and deletion (which now takes `credentials … FOR UPDATE` first, before it checks its password proof and clears the throttle row). The round-2 failure statement upserted the throttle row before updating the credentials row while every success path did the opposite, so a failed proof overlapping its owner's successful one deadlocked and PostgreSQL aborted one side (HTTP 500). As a backstop, a statement or transaction aborted with `40P01`/`40001` runs again up to three times (`db.Retry`), counted by `Store.DeadlockRetries` (tests require zero).

**Token buckets (amended after review round 3, R3-4):** the per-client and per-username buckets stay in memory per instance (the pilot runs one instance; more instances need a shared limiter, P7), in their own bounded store (200,000 buckets), apart from the v2 limiter. The v2 limiter forgets its least recently used key when full, which is harmless for its minute-scale buckets but let 50,000 cheap reads from distinct client keys (IPv6 /64s; a free /48 gives 65,536) evict an exhausted hour-scale per-username bucket and bring it back full. The v3 store never forgets a bucket that has not refilled: when full it drops a bucket that has refilled to its burst (indistinguishable from a new one), and with none it answers `429` for the new key with the time until one refills, so existing keys keep their limits. Residual: an attacker who creates buckets faster than they refill (about 200,000 within the refill time of the newest, which needs hundreds of client keys past their own per-client limits) makes new keys wait until buckets refill; existing users' buckets and the database backoff are unaffected. **Live-guest cap:** guest starts take a transaction-scoped advisory lock (`sela.guest_cap:` + schema) before counting, so concurrent starts cannot exceed `SELA_MAX_GUEST_ACCOUNTS`.

### 10. Resource-level authorization, deletion and export

- **Owner principal only from the cookie:** middleware resolves the session to `account.Principal{UserID, SessionID, Kind}`. No handler reads a user id from a path, query or body; `/me` always means the principal.
- **Every store method takes the owner:** `func (s *Store) GetX(ctx, owner account.UserID, id XID) (...)` with `WHERE id = $1 AND user_id = $2`; no owned-resource method takes only a resource id. **Cross-user access returns `404 not_found`**, never 403, so a valid id of another user is indistinguishable from a missing one. System methods (session lookup by token hash, login by username, purge, retention, rewrap) live in a separate, allow-listed interface. A reflection test checks that every method of the owner-facing store interfaces takes `account.UserID` as its first argument after `context.Context`; each feature adds cross-user tests for its methods.
- **Recipient principals** (P4): separate table, separate cookie (`__Secure-sela_recipient`, `Path=/api/v3/recipient`), each bound to exactly one share and scoped to its immutable projection; a recipient principal can never call owner routes and an owner session can never call recipient routes. Revocation, expiry and owner deletion end recipient access immediately (v2 V5/V6 semantics). Row Level Security as a second layer is deferred to the 0900 ops range (it needs separate owner and runtime roles).
- **Account deletion** (`DELETE /api/v3/me`, reauth for accounts): one transaction destroys the DEK (§5), deletes the `users` row so every owned row in every range goes by `ON DELETE CASCADE`, and commits; then the DEK cache entry is evicted, the cookie cleared and recipient access ends because the shares are gone. A schema test asserts that every table with a `user_id` column cascades from `users` (allow-list: `user_data_keys`). Logs keep no user id, so there is nothing to scrub there.
- **Export:** an exporter registry in `internal/account`: each feature registers `Exporter{Section() string; Export(ctx, tx, owner, *ExportBuilder) error}` returning structured sections (decrypted for the owner). The foundation registers `profile`, `consents`, `consent_history`, `guardian_consents`, `sessions`, `audit`. One export model is rendered as **JSON** (`format: "sela-export/1"`, machine-readable) and as readable **HTML** (self-contained, no scripts, inline CSS, localized) and **Markdown**. A registry test fails when a table with a `user_id` column is claimed by no exporter (allow-list: security-only tables `credentials`, `recovery_codes`, `user_data_keys`, whose existence is exported but never their hashes or keys). Every export writes `export.created`.
- **Revocation stops future access only.** The UI and the export say in both languages that copies already downloaded or viewed (an export file, a shared summary someone opened) cannot be recalled by Sela.

### 11. Backup and restore (engineering default; storage target pending, B-3 and B-15)

- **Two dumps per run, daily**, from one job: first the content dump `pg_dump -Fc --exclude-table=user_data_keys`, then the key dump `pg_dump -Fc --table=user_data_keys` (in this order, so every user in the content dump has a key row in the key dump; a user deleted in between appears as a tombstone, which is the safe direction). **Plus a key-only dump every hour** (`backup.sh --keys-only`; small), so a restore can see deletions made after the last content dump. All are verified with `pg_restore --list`, checksummed, encrypted at rest and stored in the hosting region. The scripts create every file `0600` in a `0700` directory under a temporary name, rename it only once verified, never overwrite one, dump with `TZ=UTC`, and pass the database password to `pg_dump`/`pg_restore`/`psql` only through a private temporary `PGPASSFILE` (never as an argument, which every local account can read), whose removal on exit is armed before the file is written (review round 2: an early exit left it behind); the database URL itself is read from an environment variable.
- **Retention:** content dumps **30 days**; key dumps **7 days** (`destroyed_at` tombstones are kept 37 days, the content retention plus a week, then deleted by the retention job). Meaning for deletion: from the moment of deletion the content is gone from the live database; within **7 days** no backup holds a usable key for it (crypto-shredded everywhere); within **30 days** its ciphertext has also aged out of the content backups. The privacy policy states exactly this.
- **Reconcile also ends sessions and orphan keys (amended after review round 2):** a content dump holds every session that was live when it was taken, including ones revoked since (logout, logout-all, revoke, the revoke step of a password change or a recovery); reconcile therefore revokes **every** session of the restored database with the reason `restored` (migration 0003) and everyone signs in again. It also destroys (tombstones, through `vault.Destroy`) every live key row without a `users` row except the operator canary's: the key of an account created after the content dump comes back live with the newer key dump while the account does not, and nothing else would ever destroy it, so any copy of that person's ciphertext (the damaged database, a newer content dump) would stay decryptable for good. `--dry-run` reports both counts (`keys without a user`, `sessions not ended`); a large orphan count means the content dump is wrong — stop. **What a restore cannot undo:** password changes, recoveries and recovery-code regenerations made after the content dump are lost (the replaced password and the used or regenerated-away codes work again), so the runbook tells users to repeat them.
- **Restore reconcile (amended after review round 1):** a restore loads the content dump together with the **newest key dump available**, never simply the content dump's own pair: `restore.sh` takes the key dump directory and uses the newest one, and refuses (as does `sela backup check`) a key dump older than the content dump. If the damaged database is still reachable, the operator first takes a fresh `backup.sh --keys-only` from it. `sela restore reconcile --dry-run` then lists the counts of users whose key row is destroyed or missing in that key table; `sela restore reconcile` deletes them through the deletion path; the dry-run prevents a wholesale deletion when the key table itself is what was lost. **Remaining window, stated honestly:** reconcile only sees deletions recorded in the key dump it is given, so an account deleted after the newest key dump was taken (at most the key-dump interval, one hour by default, when the live database is lost entirely) comes back with that restore; because deletion leaves no record outside the key table (by design, §10, §13), it cannot be identified afterwards, so the exposure is bounded by the key-dump interval (shorten it to shrink the window; a deletion journal shipped to the backup storage on every deletion would close it once B-3 decides that storage). This residual window is accepted for a controlled pilot and revisited before a public release ([D-055](../DECISION_LOG.md#d-055)). Its key and content were in the backups anyway until their retention ends. The earlier text ("a restore can never bring a deleted account back") was wrong for the same-run pair: the key dump of that run still holds the wrapped key of anyone deleted after it. The user-facing privacy text (`internal/fixtures/v3`, owned by the PM) should say this in one sentence, e.g. "If we must restore the database from a backup, an account deleted in the hour before the failure may need to be deleted again; we do that as part of the restore." The integration pass of 2026-10-26 put the sentence into `terms-privacy-2026-11-01.2` in the policy's third-person voice, with the second clause changed, because after a total loss Sela cannot identify those accounts and so cannot delete them again itself: "If Sela must restore the database from a backup, an account deleted in the hour before the failure may need to be deleted again: Sela announces every such restore in the app and on Sela's status page so that you can check." The PM confirms the sentence as written, including that second clause ([D-056](../DECISION_LOG.md#d-056)); D-055 accepts the window itself, D-056 this wording. RUNBOOK §8 has the announcement, which is planned (backlog S-262 criterion 3); the in-app notice and the status page are a gate for "ready for controlled pilot", and until they exist no restore of a pilot database may happen without a direct notice to every affected user through the app (D-056).
- **Guests at a restore (consistency fix of the integration pass, from `internal/account/lifecycle.go` and §7; accepted by the PM, [D-056](../DECISION_LOG.md#d-056); the backend owner may still refine the wording):** reconcile revokes every session, and a guest's session cookie is its only credential (§7), so after any restore every guest loses access to their guest data; no sign-in, recovery code or upgrade can reconnect a browser to it. The guest rows stay until the guest purge removes them: `last_active_at` is as of the content dump, so the purge deletes each one at most `SELA_GUEST_INACTIVE_TTL` (7 days by default) after the last activity the dump holds, or at `guest_expires_at`. A guest started after the content dump does not exist in the restored database (its key is destroyed as a key without a user). A guest deleted after the newest key dump comes back like an account, but its owner cannot delete it again; it goes with the purge. The guest notice states this (`guest-storage-2026-11-01.2`, written in the integration pass, confirmed by the PM, D-056), and so does the after-restore notice (RUNBOOK §8; backlog S-262 criterion 3).
- **Restore drill (monthly and before every data migration):** restore the latest content dump with the newest key dump into an isolated scratch database (never into staging or demo), `pg_restore --list` first, then `sela migrate status`, `sela restore reconcile --dry-run`, then decrypt the environment's synthetic canary record (`sela ops canary write|check`, created by the operator in every environment) to prove the key path works; record time-to-restore and outcome in the runbook; drop the scratch database. The synthetic drill also deletes a user **after** the backup, creates one after it and revokes a session after it, takes the later key-only dump, and asserts that reconcile deletes the deleted user, destroys the new user's key, revokes the restored session, and that a key dump older than the content dump is refused.
- **Region and data residency:** the hosting region is an **owner decision (B-15, with the host under B-3)**. The database, its backups and the KEK's secret manager live in the same region. Indonesia's Personal Data Protection Law (UU No. 27 Tahun 2022, "UU PDP") treats health data as specific personal data and sets conditions on transfer outside Indonesia and on processing children's data; the primary text could not be retrieved here (the BPK site answered 403), so no compliance claim is made and a **legal review is required before real users** (pending). If the chosen region is outside Indonesia, that review covers the transfer basis and the user-facing disclosure.

### 13. Logging and observability

The v2 rule holds and extends: slog JSON with request id, route template, status, duration, and for auth events a fixed `outcome` (`success | invalid | throttled | disabled | busy`). **Never** logged: content, usernames, passwords, recovery codes, session tokens or their hashes, user ids, guardian names, KEKs, DEKs, database URLs, IP addresses. The rule covers the database server's log too: expected conditions are detected without a failing statement (a taken username uses `INSERT … ON CONFLICT (username) DO NOTHING`, because a unique violation would make PostgreSQL log `DETAIL: Key (username)=(…)`), and the runbook sets `log_error_verbosity = terse` as defence in depth. Consent and audit records hold no client text: a withdrawal records the version of the user's last decision (never the version string sent), policy versions must match `^[a-z0-9][a-z0-9._-]{0,63}$`, and the audit helper refuses any string detail outside that shape. Content-free counters (logins by outcome, guests created/purged, deletions, exports, rewrap progress) go to the operator-only metrics route.

## Consequences

- Sela can hold real personal data; this raises the bar for operations: secret management, TLS, backups, restore drills, migration discipline and a legal review become release prerequisites, not options.
- A lost KEK (and its secret-manager copy) makes all content unreadable; KEK custody and its backup are owner responsibilities documented in the runbook.
- No server-side search or analytics over content; features decrypt per user. A DEK re-encryption tool does not exist in v1; a combined leak of key table and KEK would need it.
- One app instance for the pilot (in-memory rate limiter and DEK cache; the v2 journey store). Shared limiting is P7 work before scaling out.
- Every later feature must: put its migrations in its range with a validate file for data changes, cascade from `users`, encrypt content with AAD, list its plaintext columns, register an exporter, add cross-user tests, and add its consent purposes and policy texts.
- The memory store remains for development, demo and test; v2 journey routes are not served in staging or production.
- Pending owner, PM or legal actions (the `golang.org/x/text` approval is confirmed by the PM, D-056): B-3 and B-15 hosting, region and backup storage, the B-11 email provider blocker (optional), the legal review (UU PDP, minors and guardian consent sufficiency, cross-border transfer, provider age terms), password blocklist source, v3 policy texts (privacy, terms, guest notice, guardian information).
