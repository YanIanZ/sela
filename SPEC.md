## §G Goal

**v3 (user-confirmed, owner brief v3 §1; D-025).** Sela, *A little space to feel heard* / *Ruang sejenak untuk didengar*, continues Dengar.in as a real-use health and wellbeing app in Indonesian and English for people aged 15 to 50 and over. The core experience: "Aku memiliki ruang untuk bercerita, memahami kembali pengalamanku, dan membawa konteks yang kupilih ketika mencari bantuan" (I have a space to tell my story, understand my experience again, and bring the context I choose when I look for help).

- **Listening is the core.** A person starts talking without a long profile, gets replies that fit the context, is never pushed toward a solution and can correct how Sela understood them (V24).
- **Continuity under the user's control.** Personal notes ("Catatan pribadiku"), check-ins, memory and a timeline across sessions, kept only when the user chooses (V25–V27).
- **Help on the user's terms.** When they want to, the user prepares a sourced "Ringkasan untuk konsultasi", shares only what they select with someone they invite, stops further access, and keeps reflecting after the consultation. Seeking a professional is never required.
- Sela is not a diagnosis, treatment, triage, telemedicine or therapy service (C22). Synthetic data is for tests, evaluation and the demo only (C23).

Definition of done (user-confirmed, brief §15): the user can tell their story and get a relevant reply; choose storage; see and correct personal context; open a timeline; prepare a sourced consultation summary; control sharing; stop further access; export and delete data; continue reflecting after a consultation; use Indonesian or English; and complete the main flows with different accessibility needs. The project is not done while a main flow is mocked, the frontend is unreviewed or an important integration is unverified.

This table is the single definition of the status words. The backlog, implementation status, requirements traceability and roadmap use these words and link here instead of restating them ([conflict matrix](docs/CONFLICT_MATRIX.md#documentation-and-contract-follow-ups-open) row 54); [roadmap §2](docs/ROADMAP.md#2-release-ladder) lists the checks each level needs. Implemented is not verified; verified locally is not verified live; none of these is pilot readiness. Engineering tests are not clinical trials, and agent reviews are not user research (brief §13).

**v2 goal (implemented and verified locally; superseded as the product goal by D-025; kept as the demo configuration).** Demonstrate a bilingual mental-health care-navigation journey: enter → choose language → understand service and privacy limits → express a (synthetic or fictional practice) story → review a source-linked Story Ledger → choose a practical next step → prepare the conversation → approve what is shared → simulated handoff to a fictional professional → acknowledgement → follow-up. A Meta open-weight model powers the bounded AI steps; Go owns backend behavior.

## §C Constraints

- C2 User-confirmed: Indonesian and English across the complete journey, including error states; code-switched input is tested.
- C3 User-confirmed (v2), **superseded by D-025 (2026-10-26) → C23.** v2 text: all patient, professional, scheduling, consultation and follow-up data synthetic or fictional; no real care transaction; no contact with real professionals. It still describes the v2 demo configuration. "No real care transaction" continues in C21 and C22.
- C4 User-confirmed (amended 2026-10-26): AI uses a Meta open-weight model self-hosted on Modal.com, chosen by licence, capability and hackathon terms ([ADR-0001](docs/adr/ADR-0001-meta-open-weight-model-on-modal.md)); remove AMD integration from the v2 runtime. Preserve original authorship/license notices. *v3 (D-029): Meta stays the primary generator for every generative task but is no longer the only provider (C17). The generator model is still an owner decision ([B-7](docs/BLOCKERS.md)).*
- C5 Engineering (amended 2026-10-26): implementation phase. Go runtime, new frontend, Modal serving code, evaluation and research pipeline are built incrementally; documentation claims only what evidence shows. Paid GPU execution requires an owner-approved budget. *v3: the same rule covers every paid provider (Modal, Anthropic, DeepSeek): spend stays within an authorised budget with daily ceilings ([ADR-0003](docs/adr/ADR-0003-ai-routing-verifier-fallback.md) §11).*
- C6 Engineering default: browser product, static React/TypeScript frontend built with Vite; one Go process serves API/assets. *v3 (D-031): kept with React 19; the information architecture, interaction design and visual design are redone by the design lead.*
- C7 Engineering default (v2), **superseded by D-025 and D-026 → C15.** v2 text: session-scoped bounded in-memory store behind a storage interface; no PostgreSQL/Redis requirement, no production login, no real-data migration, no implicit persistence of sensitive data. The memory store stays for development, demo and test only. "No implicit persistence" continues as V25.
- C8 Engineering default (v2), **superseded by D-025 → C16, C18, C24.** v2 text (amended, D-003): adult-only (attested); seeded scenarios plus bounded fictional practice text; text-first. Optional transcription is out of scope until verified access/language quality.
- C9 **Superseded by D-025 → C19, C22, C24.** v2 text: New journey excludes forum, gamification, general chatbot, payments, real booking, real telemedicine, autonomous diagnosis/treatment/prescribing/triage, therapy roleplay and model training. In v3 a listening conversation is in scope (V24); the other exclusions continue in C19, C22 and C24.
- C10 No performance, deployment, clinical-quality, event-acceptance or live-inference claim without matching evidence. *v3: likewise no pilot-readiness, legal-compliance or efficacy claim; synthetic data is never efficacy evidence.*
- C11 Preserve a recoverable v1 baseline and its regression evidence before runtime replacement. Historical snapshots are context, not v2 requirements.
- C12 User-confirmed (26 Oct 2026), **partly superseded by D-025 and D-029 → C17.** v2 text: add optional Claude Sonnet 5.5 API as a **second-pass source-fidelity verifier**. Meta/Muse Spark remains the sole live *generator* and necessary hackathon contribution; Claude is not a fallback generator, clinician or source of truth. No real patient data in the hackathon. The requirement is documented and an isolated Go prototype is added, but product wiring and live access remain pending. *v3: kept: Claude is the verifier and never a fallback generator, clinician or source of truth; Meta stays the necessary hackathon contribution, with a Meta-only demo path (D-049). Superseded: "sole live generator" (DeepSeek may replace the generator on availability failures only, C17) and the synthetic-only limit outside the hackathon demo (C23). Runtime wiring is P5 (T18).* *Reconciliation (D-024), still open: C12 and the verifier contract name Muse Spark ("Muse Spark Open on Modal") as the generator; the implemented generator is the Meta open-weight Muse Glimmer 30B on Modal per C4 and [ADR-0001](docs/adr/ADR-0001-meta-open-weight-model-on-modal.md), because Muse-Spark-Open-816B-A42B is gated and needs ≥700 GB of GPU memory, beyond any approved budget. The adapter is model-agnostic; the owner decides ([B-7](docs/BLOCKERS.md), which now also lists a Modal Shared Endpoint option).*
- C13 User-confirmed (2026-10-26): anonymous or pseudonymous use; separate consent for AI processing, storage and sharing; retention and deletion that actually work. *v3: met by guest mode or a username account that needs no real name, never presented as absolute anonymity (C16); consent per AI provider (C17); persistent deletion with crypto-shredding (V32).*
- C14 User-confirmed (2026-10-26): reproducible research pipeline over the 100-publication register with a rolling five-year cutoff, provenance and rights tracking; no fine-tuning unless its prerequisites are met (D-016). *v3 (D-047): kept; the register is title/abstract-screened, not appraised; new evidence is needed for listening, journaling, consultation preparation, accessibility, adolescents' consent and confidentiality, and adults 50+; the evidence map covers the full brief §9 topic list (T19); user notes are never used for training.*
- C15 PM decision (D-026, D-027; [ADR-0002](docs/adr/ADR-0002-persistence-accounts-and-encryption.md)): **persistence and encryption.** PostgreSQL 16 through pgx v5 is the system of record, with an embedded, checksummed migrator and reserved migration ranges; the memory store is allowed only in development, demo and test. Personal content is encrypted per user (AES-256-GCM data key wrapped by a key-encryption key from the secret manager); account deletion destroys the data key (crypto-shredding). TLS in transit. Backups follow a stated policy (content 30 days, keys 7 days). Data migrations need a backup, a dry run, ownership validation and a rollback (brief §10). No personal content, recovery code or other secret is kept at rest in browser storage: the browser keeps only non-sensitive preferences, and drafts live in tab memory only (backlog BASE-11; feature matrix DX-04).
- C16 User-confirmed (brief §10) and PM decision (D-028): **accounts and guest mode.** Username and password (argon2id) with 10 single-use recovery codes and server-side sessions; no real name, email or phone number is needed. Guest mode stores data on the server; before the guest starts, the UI states where and for how long (default: deleted after 7 days without activity, at the latest 30 days after creation) and that the browser cookie is the only key. Never promise absolute anonymity. No email until a provider exists ([B-11](docs/BLOCKERS.md)).
- C17 User-confirmed (brief §8) and PM decision (D-029, D-048, D-049; [ADR-0003](docs/adr/ADR-0003-ai-routing-verifier-fallback.md)): **multi-provider AI with consent.** Roles: a Meta open-weight model on Modal is the primary generator; Claude Sonnet 5.5 (`claude-sonnet-5-5`, Anthropic Messages API) is the runtime verifier; DeepSeek (`deepseek-flash`, served version `DeepSeek-V4.1-Flash-1017`) is the fallback generator for availability failures only and, behind a default-off flag, an alternative verifier. Each provider has its own consent that names provider, processing location and purpose in plain language before first use; withdrawing one stops that provider at once; without consent the honest no-AI path remains. Data sent is minimised (V39). Claude Code is a development tool; its subscription is not application API access. Every output names its provider, and Claude or DeepSeek work is never presented or counted as Meta (D-049).
- C18 User-confirmed (brief §6) and PM decision (D-030): **minors gated.** Ages 15–17 are built (age band at onboarding, age-appropriate copy, confidentiality limits explained, a guardian consent record that grants the guardian no access, teen help resources, memory and pattern features opt-in only, no hidden monitoring, no default sharing with a guardian) but disabled in production by configuration until the legal review ([B-10](docs/BLOCKERS.md)) confirms consent and verification under UU PDP Pasal 25, PP 17/2025 (Pasal 9, 21, 22) and the provider terms. 15-year-olds stay blocked until the product is assessed as low risk under PP 17/2025 Pasal 21(1)(b). Under 15 is refused.
- C19 User-confirmed (brief §5) and PM decision (D-036): **no engagement pressure.** No streaks, points, levels, badges, quests, guilt notifications or push notifications in the pilot. Optional neutral reminders only if the user turns them on (not in pilot scope). Continuity is a calm history, never a score. Any look back over a period (the weekly reflection, after the pilot, backlog S-053) is computed only from that period's real records, in the user's language, without scores or percentages, and says whether rules or AI wrote it (feature matrix DX-11). No design that exploits vulnerability.
- C20 User-confirmed (brief §2) and PM decision (D-032): **content separation.** Public content (reading library, help directory), personal data (owned by one user, linked by ownership and consent), community content (none in the pilot), demo data (synthetic, demo environment only, labelled) and the research corpus (a separate store, never linked to any user's history) stay apart. Evaluation datasets (synthetic and labelled, in `eval/`, `internal/fixtures/` and `data/research/corpus/eval_fixtures/`) and training datasets (none exist; any proposal must pass the fine-tuning gate, backlog S-229, D-047) are further separate stores and are never derived from personal data (brief §9). Another person's story or a public article is never copied into a user's history; a reading item may be bookmarked by reference.
- C21 User-confirmed (brief §7) and PM decision (D-038, D-040, D-041): **honest terms.** "Catatan pribadiku" / "My personal notes" and "Ringkasan untuk konsultasi" / "Summary for a consultation". Never "rekam medis", "diagnosis", "hasil pemeriksaan" or "assessment result". Summaries say they are the user's own notes, prepared with AI help where that applies. A sent or opened share is not care. Recipients are people the user invites; their identity is not verified and is labelled so. No partnership, booking, directory of verified professionals or verified professional note is claimed while none exists. No invented story, count or testimonial is presented as real; any example is labelled as an example (feature matrix DX-07).
- C22 User-confirmed (brief §11) and externally sourced (UU 17/2023 Pasal 172 and 312, PP 28/2024 Pasal 558; read 2026-10-26, not legal advice): **no clinical claims or telemedicine.** Sela supports wellbeing and preparing for help. It does not diagnose, treat, prescribe, triage, score severity, provide clinical consultations, role-play therapy, present itself or its AI as a licensed professional, or claim a medical purpose. It never contacts anyone automatically.
- C23 User-confirmed (brief §1, §11) and PM decision (D-025, D-045): **real use and environment separation** (replaces C3). Sela supports real use. Synthetic data is for tests, evaluation and the demo only. Environments are development, test, demo, staging and production (V40). The demo runs every feature for real on synthetic data; its AI uses live providers on synthetic data or labelled test doubles (D-045). The v2 fictional professionals, scenarios and plans stay in the demo configuration only (D-041).
- C24 PM decision (D-037, D-042) under brief §2 ("do not remove features only to make the refactor easier"): **pilot scope with reasons** (replaces the C9 list). Retired: severity assessment and pathway labels, gamification, the 14-day path, the OpenRouter debiaser, AMD, the AI reply cache, and the Supabase and forum persistence. Paused, with prerequisites recorded in the backlog: the anonymous forum and its moderation, and the Gemini voice room. Deferred: document uploads. Opt-in: voice dictation (disclosure that the browser's speech service may send audio to its vendor, editable transcript, no autoplay) and local read-aloud. Out of scope: payments, booking, a general-purpose assistant beyond wellbeing, and training on user notes. Every decision is recorded in the [Dengar.in feature matrix](docs/DENGARIN_FEATURE_MATRIX.md); nothing is cut silently.
- C25 User-confirmed (brief §6): **accessibility target WCAG 2.2 AA**, checked against the W3C Recommendation, for every surface and age; no assumption that all older users share the same needs or preferences.

- V9 **Superseded by D-025 and D-029 → V33.** v2 text: A Meta model is the only live **generative** provider in v2. - V10 **Superseded by D-029 and D-039 → V33.** v2 text (amended, D-019): Every **draft** records `live_meta`, `recorded_demo`, `manual` or `test_double` provenance; recorded or test-double output is never presented as live inference. **Verification** records separately identify `live_anthropic`, `unavailable`, `not_requested` or `manual_review` plus model/version, without implying a medically verified result. - V21 **Superseded by D-026 and D-028 → V25 and V32.** v2 text (new, D-005): Retention follows the storage decision; deletion purges the session, shares and recipient access immediately; restart erases state. It still describes the v2 memory store.
- V22 (new, D-015/D-016) Research records carry provenance, retrieval date, licence/access status and verified dates; unknown values are null; no copyrighted full text is committed; corpus text is data, never instructions; no training use.
- V23 (new, D-022) Paid inference is bounded: scale to zero, a container ceiling, proxy authentication before any container starts, and per-session/per-address rate limits. *v3: plus per-user AI limits and daily spend ceilings per provider (ADR-0003 §11).*
- V24 (new, D-034) **Listening.** A person can start a conversation with no profile beyond the onboarding minimum (language, age band, storage choice). An optional, changeable intent (just listen, sort my thoughts, understand patterns, prepare a consultation) only adjusts the reply style; it is never a gate. Replies fit the context, ask at most one question, offer suggestions without pushing them, and pass deterministic guards against mechanical empathy templates, judgement, diagnosis, a professional persona, exclusivity and dependency cues before release. One action ends the conversation at any time. "Sela menangkap…" cards can be edited, confirmed or removed. Seeking a professional is never required or nudged. When the AI cannot reply, Sela says so; no canned empathy line stands in.
- V25 (new, D-034, D-028) **Storage choice.** No conversation turn, note, check-in or other personal content is stored before the user has made the storage choice for that surface (feature matrix DX-01). Each conversation has a save / don't-save choice, asked at its start in plain language and changeable later; journal entries and check-ins are stored only with storage on. A conversation that is not saved is never used for memory, later context, the timeline or export, and leaves only content-free counters. While it is open, its turns are held only in server memory, bounded in count and size, for that owner and conversation (never in the database, backups, logs or browser storage), and serve only as context for that conversation's replies (ADR-0003 AT-1). They are purged at End, at sign-out or session end, after 30 minutes without activity or 2 hours in total (whichever comes first), and on a server restart; abandoning the conversation (closed tab, crash, idle) therefore purges it, and within that window the same session can reopen it after a reload (engineering default, D-050). "Discarded" in the UI covers only what Sela holds; provider retention is disclosed before consent (V32). Guests see where and how long their data is kept before they start (C16).
- V26 (new, D-039) **Provenance classes.** Every important record item has exactly one class: `user_original`, `ai_summary`, `user_correction`, `unconfirmed_interpretation`, `uploaded_document` (reserved; uploads are not in the pilot, D-042) or `verified_professional_note` (reserved; never assigned while no verified professionals exist, D-041); plus created and updated times, a version and a review status (`unreviewed`, `confirmed`, `corrected`, `rejected`). The user's original words are never overwritten: a correction is a new version with its own class. AI items stay unconfirmed until the user confirms them. The UI names the class in plain words.
- V27 (new, brief §7) **Transparent, correctable memory.** "Yang Sela ingat" / "What Sela remembers" holds only items the user confirmed or added, and only with the `personal_memory` consent. The user sees each item with its source and provenance, can edit, confirm, reject or delete it, and can turn memory off. Deleting a source removes items derived only from it and marks dependent summaries stale. No hidden profile exists outside this view. For minors memory is opt-in only (V35).
- V28 (new, D-040, D-041) **Sharing consent by content, recipient and purpose.** A share is created only after the user sees the exact immutable projection and consents explicitly to the selected items, the recipient label, a purpose from a fixed list, a duration and the current sharing-policy version; a changed selection, recipient, purpose or summary version needs a new consent. A consultation summary contains only what the user selected and never adds a diagnosis, medication, trauma or history the user did not write. Handoff statuses are `prepared → shared → opened → acknowledged → consultation_in_progress`, plus `revoked`, `expired` and `ended`; no status says or implies that care was given. The recipient needs the link token and a separate access code; the recipient's identity is not verified and the recipient page says so.
- V29 (new, brief §7) **Revocation semantics.** Revocation, expiry, replacement of a share and account deletion end every future access at once, including recipient principals. They cannot recall copies already downloaded, exported, printed or viewed; the UI, the export and the policy say so in Indonesian and English, and Sela never claims to have retracted them.
- V30 (new, brief §7) **Access audit.** Every recipient access (each view, not only the first), share creation, revocation and expiry, export, consent change, sign-in, session revocation, recovery-code use and guardian-consent record writes an append-only audit event the owner can see. Events hold only allow-listed, content-free details: never content, tokens, codes, passwords or IP addresses. Operator access is audited too (engineering default, D-051): every operator command that can reach personal data or keys (`sela keys`, such as a rewrap; `sela restore` and its reconcile; the restore drill's canary decryption; data migrations) and every operator change to a user's record (such as withdrawing a guardian consent) writes an append-only, content-free operator audit record (command, environment, operator identity, time, outcome, counts), and an operator change to one user's record also appears in that user's own audit. Direct database sessions in staging and production are recorded by the database host's access log (hosting choice, B-3). No route or tool shows an operator a user's decrypted content.
- V31 (new, brief §7, §10) **Isolation.** The owner principal comes only from the session cookie; no route takes a user id from the client; every owned-resource read or write is bound to the owner, and another user's resource answers `404 not_found` and changes nothing. Owner and recipient principals never cross. The server refuses a database or key from another environment (instance marker, key-id prefix).
- V32 (new, D-027, brief §7) **Deletion with derivatives.** Deleting an item deletes what was derived only from it (AI outputs, memory items, verifier records) and marks summaries that cited it stale; deleting a summary ends its shares. Deleting an account, or purging an expired guest, removes every owned row in one transaction, ends all shares and recipient access, and destroys the user's data key. After deletion no backup holds a usable key within 7 days and the ciphertext ages out of backups within 30 days; a restore never revives a deleted account. Copies held by AI providers follow the provider retention disclosed before consent.
- V33 (new, D-029; ADR-0003 RR-1 to RR-16) **Routing and provenance.** Meta on Modal is the primary generator for every generative task. DeepSeek replaces it only after an availability failure before any content arrived (cold start beyond budget, 5xx, timeout, capacity, an authentication failure on Sela's side), only with the DeepSeek consent, an `18_plus` age band and the fallback enabled; never after a refusal, safety block, Meaning Lock rejection, guard rejection or any other content-based failure; at most one switch per operation. Claude never generates. Every call is preceded by a consent, age-band, limit and kill-switch check; a result whose record, consent or crisis state changed is discarded (V20). Every AI output records provider, model id, served version, route, verifier verdict and latency. Draft provenance: `live_meta`, `live_deepseek`, `recorded_demo`, `manual` or `test_double`. Verification provenance: `live_anthropic`, `live_deepseek_alternative`, `test_double`, `unavailable`, `not_requested`, `not_required` or `manual_review`. `test_double` records a report from a labelled test-double verifier ("TEST DOUBLE — not Claude" or "TEST DOUBLE — not DeepSeek"), which exists only in development, test and the demo (D-045, ADR-0003 §10.1) and is refused in production (V40); it is never stored or shown as a check by Claude or DeepSeek (SPEC amendment under D-045; [conflict matrix](docs/CONFLICT_MATRIX.md#documentation-and-contract-follow-ups-open) row 58). The UI labels each output's provider; test-double or recorded output is never presented as live, and Claude or DeepSeek output never as Meta. A switch is never silent: a fallback output is labelled as such, and when no permitted provider is available the UI shows the honest unavailable or manual state. Provider keys stay server-side; every provider request is bounded in size, cancellable, time-limited and admission-limited (V11, V20, V23).
- V34 (new, D-029; ADR-0003 §6) **Verifier.** AI wording in consultation summaries, AI memory proposals and any generated text flagged by the deterministic health-claim detector are verified before release; reading content is verified at authoring time with human sign-off. Verdicts are `supported`, `unsupported`, `contradicted` or `insufficient_evidence`, each with a short reason and the source spans checked; only `supported` claims without an issue are released, others fall back to the user's own words or are dropped. The verifier needs its own consent; without it there are zero verifier calls. A model never verifies its own output: DeepSeek may be the alternative verifier only when Claude is unavailable, Meta generated the output, the user consented to DeepSeek and the default-off flag was enabled after evaluation, and its verdicts are labelled. With no permitted verifier, verifier-gated output is withheld, the user's words are kept, the manual path is offered and the UI says why. No chain-of-thought is requested or stored. A verdict never overrides deterministic guards, user review, consent, approval or sharing (V17); agreement between models is not clinical evidence.
- V35 (new, D-030) **Minors.** The age band is self-declared (`15_17`, `18_plus` or `unknown`); "under 15" stores nothing and shows help information. Bands outside the configured list are refused; production allows only `18_plus` until B-10 clears minors, and 15-year-olds stay blocked until the low-risk assessment (C18). `unknown` gets the protective defaults of `15_17`. For `15_17`: age-appropriate copy; confidentiality limits explained before use; a guardian consent record that gives the guardian no account, access, notification or export; nothing shared with a guardian by default; memory and pattern features opt-in only; teen help resources verified as in V37; no DeepSeek as generator or verifier; no hidden monitoring.
- V36 (new, D-035; extends V3) **Crisis handling.** The deterministic lexicon screens every user text before storage and before any model call, and each assessment records the ruleset version. A crisis match never erases what the user wrote and never navigates away: inline verified help and a link to Immediate help appear, AI generation for that conversation pauses until the user chooses to continue after seeing help, and the text is kept only if the storage choice allows. Journal and check-in entries that match are saved (with storage on) and shown with support, never refused. Second safeguards beyond the lexicon: an always-visible "Butuh bantuan sekarang" / "Need help now" control, Quick exit, the generator's structured risk flag that can only raise the route, the verifier's `safety_signal` issue, and user review of anything shared. Crisis support never waits for a model. Sela never contacts anyone automatically.
- V37 (new, D-043) **Verified help resources.** Only entries verified from official sources are shown, each with source, verification date and a re-verify-by date that the server enforces; a stale entry is flagged, never shown as current. Teen entries need the same verification; the unverified KPAI WhatsApp contact is not shown. No number or service is invented. One catalogue serves every surface.
- V38 (new, brief §7) **Export.** The user can export all their data at any time as readable (HTML, Markdown) and structured (JSON `sela-export/1`) files with provenance, versions and dates. User text is escaped; every export is audited; password, code and token hashes and keys are never exported; the export says downloaded copies cannot be recalled.
- V39 (new, ADR-0003 §9) **Data minimisation for AI providers.** A provider receives only the text segments its task needs, with contact details and names the user marked private replaced by placeholders, per-request span ids and no account, user, session or database identifiers. A conversation the user did not save is never sent for memory. Logs hold metadata only (V12).
- V40 (new, D-045) **Environment separation.** Development, test, demo, staging and production are separate. Production refuses the memory store, test doubles, demo fixtures, insecure cookies and missing secrets. Demo and staging hold synthetic data only. The demo shows a synthetic-data banner and really runs every feature; its AI uses live providers on synthetic data or labelled test doubles (D-045), and test-double output is labelled, never presented as live (V33). ADR-0002 §12 and the uncommitted `internal/config` guard currently refuse the test double in the demo, which is narrower than D-045; D-045 governs, and the two are being aligned with it ([conflict matrix](docs/CONFLICT_MATRIX.md#documentation-and-contract-follow-ups-open) row 52). Demo data never appears in production, and production data is never copied to another environment.
